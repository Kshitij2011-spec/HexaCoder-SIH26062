# Canonical Domain Language & Glossary

This document establishes the official, unambiguous terminology of the SIH26062 Antarctic & Polar Expedition Operational Logistics Platform.

Both Person A and Person B must use these exact terms across database models, API schemas, frontend labels, variable names, and documentation.

---

## 1. Canonical Domain Concepts

| Term | Definition | Primary Key / Code Format |
|---|---|---|
| **Expedition** | Top-level polar deployment campaign (e.g. 45th Indian Scientific Expedition to Antarctica) spanning an operational season. | `EXP-<YY>-<SUFFIX>` (e.g., `EXP-26-A`) |
| **Mission** | An operational, scientific, or logistical objective executed within an expedition, constrained by temporal windows and resource requirements. | `M-<NN>` (e.g., `M-08`) |
| **Person** | An authenticated participant (scientist, logistics officer, station commander, pilot) assigned to expedition roles. | `PER-<NNN>` |
| **Team** | A structured operational group of personnel formed to execute one or more missions (e.g., Deep Field Traverse Team). | `R-<NN>` (e.g., `R-04`) |
| **Cargo Consignment** | A high-level aggregate shipment grouping multiple individual packages for transport across polar legs. | `CON-<NNN>` |
| **Cargo Package** | An individual physical container, drum, or crate with specific dimensions, weight, handling class, and hazmat code. | `PKG-<NNN>` |
| **Inventory Stock Lot** | A tracked batch of consumable supplies, fuel, medical rations, or critical spares stored at a specific station or depot. | `LOT-<NNN>` (Item: `I-42`) |
| **Asset** | High-value, durable capital equipment (snowmobiles, PistenBullys, Twin Otter aircraft, lab analyzers) requiring tracked maintenance. | `AST-<NNN>` |
| **Transport Leg** | A discrete, scheduled movement segment connecting two polar locations via a specific transport mode (Vessel, Fixed-Wing, Traverse). | `T-<NN>` (e.g., `T-08`) |
| **Location** | A geographic waypoint, Antarctic research station (Maitri, Bharati), ice runway, or field cache with coordinates and capability flags. | `LOC-<CODE>` |
| **Incident** | An unexpected polar event (equipment breakdown, blizzards, route obstruction, medical emergency) requiring intervention. | `INC-<NNN>` |
| **Operational Event** | An immutable, auditable record emitted on every state mutation capturing previous state, new state, actor, evidence, and correlation ID. | `evt_<uuid>` |
| **Dependency** | A directed, typed semantic link (`REQUIRES`, `SUPPORTS`, `MOVES_VIA`, etc.) connecting two entities in the operational graph. | Semantic Edge |
| **Constraint** | A hard or soft boundary (weather cutoff, payload ceiling, mandatory crew rest, cold-chain threshold) governing feasibility. | `C-<NNN>` (e.g., `C-117`) |
| **Replan** | An operational re-evaluation triggered by an impact to a dependency chain when a constraint is violated or manual review is requested. | `RPL-<NNN>` |
| **Recommendation** | An advisory proposal generated by deterministic solvers or heuristics suggesting resource re-allocations or schedule shifts. | `REC-<NNN>` |
| **Approval** | The formal, immutable record of an authorized human operator accepting, rejecting, or modifying an advisory recommendation. | `APP-<NNN>` |
| **Response Action** | A concrete corrective operational assignment created to mitigate an active incident. | `ACT-<NNN>` |
| **Time Window** | A temporal interval defining operational validity (e.g., polar weather flight window, station resupply window). | `WIN-<NNN>` |

## 2. Strictly Forbidden Terminology & Prohibited Aliases

To preserve architectural precision and protect the judging narrative, the following loose terms are strictly banned from UI labels, API endpoints, and schemas:

| Prohibited Colloquialism | Why It Is Prohibited | Mandatory Canonical Term |
|---|---|---|
| **Shipment** | Inaccurate in polar logistics; legs are multimodal, segmented, and multi-stage. | **Transport Leg** (or **Cargo Consignment**) |
| **Mission Status** (for readiness) | Confuses overall lifecycle state (`PLANNED`, `ACTIVE`) with evaluated resource feasibility. | **Mission Feasibility / Readiness** |
| **Available Inventory** (for on-hand) | Conflates total physically present stock with unreserved, unallocated stock. | **Unallocated Stock** / **On-Hand Quantity** |
| **Live GPS / Live AIS** | Violates Data Honesty Rule (no live hardware satellite telemetry claim in MVP). | **Estimated Position (DERIVED / SCENARIO)** |
| **Autonomous Action / AI Execution** | Violates Human Approval Rule (system recommends, human operator approves). | **Recommendation (ADVISORY)** |
| **Driver / Chauffeur** | Inappropriate for polar traverse or heavy machinery. | **Operator / Traverse Pilot** |
| **Trip** | Trivializes high-risk expedition logistics segments. | **Transport Leg / Traverse** |
| **Linked to** (generic) | Violates Dependency Rule (untagged, generic relational links are forbidden). | Explicit verb: `REQUIRES`, `SUPPORTS`, `MOVES_VIA`, etc. |

## 3. Data Provenance Vocabularies

Every operational record displayed on the frontend or returned via API must declare its provenance attribute:

- `MEASURED`: Directly recorded field measurement (e.g. station weight check, physical inventory audit).
- `DERIVED`: Deterministically computed by software logic (e.g. remaining fuel consumption rate).
- `FORECAST`: Projected based on weather window models or scheduling calculations.
- `SCENARIO`: Pre-configured evaluation state injected for testing or simulation.
- `SYNTHETIC_DEMO`: Deterministic benchmark mock data generated for MVP verification.
- `ADVISORY`: Recommendation output from heuristic solvers requiring human approval.
